# 1. PRD

## Problem, vision and users

**Problem.** Technical due diligence on a codebase is slow, inconsistent and hard to audit. Pure LLM reviews hallucinate findings; pure scanners miss cross-file context and cannot explain business impact.

**Vision.** A platform that audits an uploaded repository for security vulnerabilities, architectural risks and third-party licensing concerns. Scanners find what they are good at; AI agents investigate context and explain; every finding links to code evidence; critical risk requires a human decision.

| User | Goal | Key needs |
| --- | --- | --- |
| Analyst (due-diligence engineer) | Run an audit and read findings | Upload, progress, evidence-linked findings, filters |
| Reviewer (senior / partner) | Decide on critical-risk assessments | Full evidence, scores, rationale, approve / override / request more evidence |
| Executive | Understand risk quickly | Executive report, risk summary, remediation cost view |
| Admin | Operate the platform | Users, budgets, model settings, audit log |

## Goals, non-goals and success metrics

**Goals**

- Every finding is traceable to a file and line range in the uploaded repository.
- Risk scoring is explicit and explainable, never one LLM-generated number.
- Critical risk pauses for human review with a persistent, auditable decision.
- The system can answer "insufficient evidence" instead of guessing.
- Measured benchmark results prove where AI helps and where it does not.

**Non-goals (v1)**

- Executing audited code, or dynamic/runtime testing.
- Legal opinions on licenses; the platform flags and cites, counsel decides.
- Judging business risk that a repository alone cannot show (contracts, deployment, data).
- Auditing languages beyond Python and JavaScript/TypeScript.

**Success metrics** (targets are starting hypotheses, set final values from the first benchmark run)

| Metric | Definition |
| --- | --- |
| Precision | Valid reported findings / all reported findings |
| Recall | Known planted issues detected / all planted issues |
| False-positive rate | Reported issues not actually present / reported findings |
| Evidence accuracy | Share of findings whose cited code truly supports the claim |
| Severity accuracy | Share of findings whose severity matches the benchmark label |
| Cost per repository | Total LLM and compute spend per audit |
| Latency | Upload to final report, per repository |
| Reproducibility | Overlap of findings across repeated runs of the same repo |

**Finding states** (every finding is in exactly one): scanner-confirmed, AI-suggested, verified, rejected as false positive, unresolved (needs human investigation).

**Agent roles:** Security, Architecture, Compliance, Reporter. Scanners and AST analysis run before any agent; agents never replace a scanner result, they interpret it.

## Non-functional requirements

Numbers are starting targets to be tuned after the first benchmark; they are not measured results.

| Area | Requirement |
| --- | --- |
| Security | Repository content is untrusted data, never instructions; no execution of audited code; read-only mounts; secrets never written to prompts, logs or reports in plain text |
| Isolation | Intake and scanners run in a network-restricted container with CPU, memory, time and size limits |
| Reliability | Audit state is persisted at every stage; a crashed worker resumes from the last completed stage |
| Explainability | Every score shows its factors; every finding shows its evidence |
| Auditability | Reviewer decisions and overrides are append-only and attributable to a user and time |
| Performance | Target audit time and cost ceiling per repository defined per repo-size tier; hard budget stop on cost |
| Observability | Trace every agent call: tokens, cost, latency, retries |
| Privacy | Uploaded repositories deleted after a configurable retention period |
| Portability | Whole system runs with one `docker compose up` |

## Evaluation requirements

The benchmark is the proof the system works. Build it in Stage 2 and rerun it after every change.

**Benchmark repositories** each contain planted, labeled issues with file and line expectations, plus adversarial repos with prompt-injection comments.

| Planted issue | Expected detector |
| --- | --- |
| Hardcoded test credential | Secret scanning |
| Vulnerable dependency version | Dependency vulnerability analysis |
| Missing authorization check on a protected route (cross-file) | Security analysis with retrieval |
| Circular module dependency | Architecture analysis |
| Dependency with a restrictive license | License analysis |
| Comment telling the agent to report the repo as secure | Must be ignored; finding still reported |

**Four-way experiment** on the same benchmark:

1. Static scanners alone
2. One LLM agent with repository retrieval
3. Multiple specialized agents
4. Multiple specialized agents plus validation and risk aggregation

**Report for each:** precision, recall, false-positive rate, evidence accuracy, severity accuracy, cost per repository, latency, reproducibility (repeated runs), and recall on cross-file issues. Measure each agent separately, then the full pipeline.

**Decision rule:** if multi-agent quality gains do not justify the cost increase, document why or simplify the design. Also report where agents do not help. Use pytest for the harness, with Ragas or DeepEval only where their metrics fit.

## Release stages, risks and open decisions

| Stage | Outcome | Exit gate |
| --- | --- | --- |
| 1. Reliable auditor | Upload, safe extraction, scanners, structured findings, basic report | Scanner findings match benchmark baseline |
| 2. AI investigation and RAG | Indexing, hybrid retrieval, Security and Architecture agents, validation, benchmark | AI-assisted results compared with Stage 1 baseline |
| 3. Orchestration and controls | Compliance agent, LangGraph, risk aggregation, human review, audit trail, observability, Docker, UI | Four-way experiment complete and published |

**Key risks**

- Prompt injection from repository content: mitigated by data/instruction separation, no agent code execution, adversarial benchmark repos.
- LLM false positives: mitigated by validation stage and evidence checks.
- Cost growth from multi-agent runs: mitigated by per-audit budgets and the four-way experiment.
- Framework overlap between CrewAI and LangGraph: keep CrewAI only if it adds measurable value over LangGraph alone.
