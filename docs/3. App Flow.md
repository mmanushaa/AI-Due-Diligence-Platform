# 3. App Flow

## Primary user journey

An analyst takes a repository from upload to a finished report; a reviewer joins only when the risk is critical.

1. **Sign in.** Analyst logs in and lands on the Dashboard.
2. **Upload.** Analyst drops a zip or enters a Git URL on Repositories. The client checks size; the server validates and stores a read-only snapshot.
3. **Start audit.** Analyst clicks Start audit. The audit is queued and the Audit progress screen opens with a live stage tracker.
4. **Watch progress.** The tracker updates over SSE through intake, indexing, scanners, agents, validation and risk scoring. Cost so far is shown.
5. **Explore findings.** Findings appear grouped by category and severity. The analyst opens a finding to see code, evidence, reasoning and recommendation.
6. **Check the score.** The analyst opens the Risk breakdown to see each factor behind the overall level.
7. **Review gate (critical only).** If the overall level is critical, the audit moves to `awaiting_review`. A reviewer opens the Review detail, checks evidence and rationale, then approves, overrides with a reason, or requests more evidence.
8. **Finalize.** Non-critical audits finalize straight away. Critical audits finalize after the reviewer decision.
9. **Read and share.** Analyst or executive opens the Executive report, downloads the PDF, and the audit trail records every step.

**Request more evidence loop:** the audit status becomes `needs_evidence`, the analyst adds notes or re-runs a stage, and the run returns to validation and risk scoring before another review.

## Screens, navigation and error paths

| Screen | Reached from | Leads to | Roles |
| --- | --- | --- | --- |
| Login | App start | Dashboard | all |
| Dashboard | Login, nav | Repositories, Reviews, Audit detail | all |
| Repositories + upload | Nav | Audit detail (after starting audit) | analyst, admin |
| Audit progress | Start audit | Findings, Review status, Report | analyst |
| Findings list | Audit detail | Finding detail | analyst, reviewer |
| Finding detail | Findings list | Findings list; review screen when critical | analyst, reviewer |
| Risk breakdown | Audit detail | Finding detail | analyst, reviewer |
| Review queue | Nav | Review detail | reviewer |
| Review detail | Review queue | Decision, back to queue | reviewer |
| Report | Audit detail | PDF download | analyst, reviewer |
| Audit log | Audit detail, nav | none | reviewer, admin |
| Benchmark results | Nav | Run detail | admin |
| Settings (users, budgets, models) | Nav | none | admin |

**Review decision paths**

| Reviewer action | Result |
| --- | --- |
| Approve | Assessment finalized as computed; decision stored with user and time |
| Override | Reason required; reviewer sets a different level or marks findings rejected; original and new values both kept |
| Request more evidence | Audit marked `needs_evidence`; analyst notified; run resumes after new notes are added |

**Error and edge paths**

| Situation | Behavior |
| --- | --- |
| Invalid or malicious archive | Upload rejected before intake with a clear reason |
| One scanner fails | Run continues; report and progress show that source as failed |
| LLM provider outage | Retry, then fall back model, then mark affected findings unresolved |
| Cost budget reached | Run stops cleanly; partial results kept and labeled incomplete |
| Worker crash | Run resumes from last saved stage |
| Evidence incomplete | Verdict shown as "insufficient evidence", never as pass |
| No reviewer acts | Audit stays in `awaiting_review`; reminder shown in queue |
