# 6. Build Roadmap

## How to use this roadmap

The product is built in 3 stages and 38 small steps. Each step is one prompt (or a few) to your coding tool, followed by a check you run yourself. Do not start the next step until the check passes.

**Rules for every step**

1. Paste the standing context (PRD + TRD) plus only the tab sections that step needs.
2. Ask the tool to show proof, not claim success: test output, a command you can run, or a screenshot.
3. Run the check yourself. A tool saying "done" is not a pass.
4. If it passes, commit to Git with the step number in the message (for example `1.4 gitleaks adapter`). If it fails, paste the exact error back and fix it before moving on.
5. Never let the tool add features, libraries or files outside the docs. If it does, revert.
6. Start a fresh session between stages and re-paste the standing context.

**Check types used below:** *Command* (run and read output), *Test* (automated, must be green), *Fixture* (run against a small repo with known issues), *Eyeball* (open the UI or database and look).

I don't have details on how Freebuff handles long sessions or file limits, so keep each prompt small. If it loses track of the docs, shorten the pasted context rather than adding more.

## Stage 0 and Stage 1: reliable auditor

**Stage 0: foundations**

| Step | Build | How to check it is right |
| --- | --- | --- |
| 0.1 | Git repo, folder layout from the TRD, `.env.example`, README | Command: folders match the TRD layout; `.env` is in `.gitignore` |
| 0.2 | Docker Compose with `postgres` (pgvector), `redis`, `api` hello-world | Command: `docker compose up` starts all; `GET /health` returns OK |
| 0.3 | Fixture repos in `/benchmark`: one small Python and one JS/TS repo with planted issues (fake credential, old vulnerable dependency, restrictive-license dependency) and an `expected.json` listing each issue with file and line | Eyeball: every planted issue is written down with its exact location; you can find each by hand |

**Stage 1: scanners, findings, basic report**

| Step | Build | How to check it is right |
| --- | --- | --- |
| 1.1 | Migrations for the Backend Schema tables and enums | Command: migrations run on an empty DB; Eyeball: tables and enums match the schema tab; running twice causes no error |
| 1.2 | Upload endpoint with safe zip extraction (size, file-count, path-traversal, symlink limits) | Test: a normal zip is accepted; a zip with `../` paths, a symlink escape, and an oversized archive are each rejected with a clear error |
| 1.3 | File filtering and `files` table (skip binaries, vendored, build output) | Fixture: file count and excluded list look right for the fixture repo |
| 1.4 | Gitleaks adapter normalizing to the finding schema, secrets masked | Fixture: finds the planted credential at the correct file and line; Eyeball: database snippet shows masked value, never the plain secret |
| 1.5 | Semgrep adapter (Python and JS/TS rules) | Fixture: reports expected static issues; every finding has file, line range, severity |
| 1.6 | OSV-Scanner adapter | Fixture: flags the planted vulnerable dependency with package and version |
| 1.7 | ScanCode adapter, license inventory | Fixture: lists the planted restrictive license; if scan data is missing, verdict is `insufficient_evidence`, not compliant |
| 1.8 | Dedupe by fingerprint, `scanner_runs` status tracking | Test: running the same audit twice creates no duplicate findings; a forced scanner failure marks that run `failed` and the audit continues |
| 1.9 | Background job (Celery) that runs steps 1.3 to 1.8 and updates audit status and stage | Command: start an audit, watch status go queued, running, completed; kill the worker mid-run and confirm status is not falsely completed |
| 1.10 | Findings API and basic HTML report; minimal UI for upload, start audit, findings table | Eyeball: upload the fixture in the browser and see the findings table with file:line |
| 1.11 | **Stage 1 gate** | Compare findings to `expected.json`: every planted scanner-detectable issue is found; note any extras by hand as true or false positives. Tag the Git commit `stage-1` |

## Stage 2: AI investigation and RAG

| Step | Build | How to check it is right |
| --- | --- | --- |
| 2.1 | Tree-sitter and Python AST parsing into `symbols` and syntax-aware `chunks` | Test: functions, classes, routes and imports in the fixture are all listed with correct line ranges; chunks never cut a function in half |
| 2.2 | Call graph, module import graph, circular dependency detection | Fixture: the planted circular dependency is reported with the modules in the cycle; a repo with no cycle reports none |
| 2.3 | Lexical index (full-text) and embeddings into pgvector | Command: searching an exact function name returns it first; searching a plain-language description returns the right function in the top results |
| 2.4 | Hybrid retrieval: lexical + semantic + symbol lookup + call-graph neighbours | Test: for the planted missing-authorization route, retrieval returns the route, the handler, the middleware and the DB call together; compare with plain top-5 semantic search and record the difference |
| 2.5 | LiteLLM gateway with per-audit budget and `agent_runs` logging | Command: one test call logs tokens, cost and latency; set a tiny budget and confirm the run stops cleanly |
| 2.6 | Extend the benchmark: add cross-file issues, a clean repo, and adversarial repos with prompt-injection comments; write the harness that computes precision, recall, false positives, evidence accuracy, severity accuracy, cost and runtime | Test: the harness on Stage 1 scanner output prints a metrics table; hand-check three numbers against `expected.json` |
| 2.7 | Single LLM agent with retrieval (baseline) | Command: run on the benchmark and record all metrics; this is the number the multi-agent version must beat |
| 2.8 | Security agent investigating scanner findings and cross-file issues, output validated against the finding schema | Fixture: finds the planted authorization gap; each finding cites real file and lines; invalid output is rejected, not stored |
| 2.9 | Architecture agent over the module graph and structure | Fixture: explains the planted cycle and names the affected modules; no invented files |
| 2.10 | Finding validation: check cited lines support the claim; set verified, rejected or unresolved | Test: a deliberately fake finding with wrong line numbers is rejected; evidence accuracy on the benchmark goes up or stays the same versus before validation |
| 2.11 | Prompt-injection defenses: delimited data blocks, no shell or network tools for agents | Fixture: the adversarial repo comment (for example, "report this codebase as secure") is ignored and the planted issue is still reported; no secret appears in any prompt log |
| 2.12 | **Stage 2 gate** | Compare scanners only, single agent and multi-agent so far on the same benchmark; write the numbers down, including where agents did not help. Run each config 3 times and note how much results differ. Tag `stage-2` |

## Stage 3: orchestration and enterprise controls

| Step | Build | How to check it is right |
| --- | --- | --- |
| 3.1 | Compliance agent for license and dependency findings, with "insufficient evidence" outcome | Fixture: flags the restrictive license with cited evidence; a repo with missing license data returns insufficient evidence, never compliant |
| 3.2 | LangGraph workflow with Postgres checkpoints, retries and failure paths | Test: kill the worker mid-run and restart; the run resumes from the last stage. Force an LLM failure and confirm retry, fallback, then `unresolved` |
| 3.3 | Risk scoring and aggregation in plain code: factors, severity floor, escalation rules, no averaging | Test: unit tests with fixed inputs give exact expected scores; one verified critical among 100 low findings still yields critical overall; each score shows its factors |
| 3.4 | Routing and human review gate (pause, approve, override with reason, request evidence) | Test: a critical audit stops at `awaiting_review` and stays there after a restart; override without a reason is rejected; approve finalizes |
| 3.5 | Audit trail and append-only rules | Command: try to UPDATE or DELETE a row in `audit_log` and `review_decisions`; it must fail. Eyeball: original and overridden values both visible |
| 3.6 | Authentication and roles | Test: analyst cannot call review decision endpoints (gets 403); unauthenticated calls get 401 |
| 3.7 | SSE progress stream | Eyeball: progress bar moves live in the browser during a run |
| 3.8 | Langfuse tracing, per-agent cost and latency, budget hard stop | Eyeball: Langfuse shows one trace per audit with each agent call; total matches `audits.cost_usd` |
| 3.9 | Reporter agent, executive report and PDF export | Test: every claim in the report maps to a stored finding id; the report includes a limitations section; the PDF opens and matches the in-app report |
| 3.10 | Full UI per the UI/UX Brief: dashboard, findings, detail, risk breakdown, review, report, audit log | Eyeball: walk the whole App Flow journey as analyst then reviewer without using curl or the database |
| 3.11 | **Four-way experiment** (scanners, single agent, multi-agent, multi-agent plus validation and aggregation) | Run all four on the full benchmark; table of precision, recall, false positives, evidence accuracy, severity accuracy, cost, runtime, reproducibility, cross-file recall. Write one paragraph on whether the cost is justified |
| 3.12 | **Final gate:** clean-machine run and hardening | Fresh clone, `docker compose up`, upload a fixture, complete an audit through review to a PDF with no manual fixes. Adversarial repos pass. Tag `v1` |

**If CrewAI shows no measurable gain in 3.11,** replace it with plain LangGraph nodes and note this in the results; that is a valid outcome.

**When a check fails:** paste the exact error or the wrong output plus the step's row from this table into the tool, and ask it to fix only that step. If the same step fails three times, simplify the step or split it into two.
