## System architecture

&#91;embedded content: system architecture · 8 components\]

The API only enqueues work and reads results; the worker runs the LangGraph workflow, which calls the network-less scanner sandbox first, then agents that retrieve code context and reach models only through the gateway.

## Pipeline design

**Principle:** deterministic tools detect what they already do well; LLM agents interpret context, investigate ambiguous cases, explain impact and prioritize. Minimum sufficient intelligence: rules first, small models for triage, larger models only for cross-file reasoning.

| # | Stage | What happens | Output |
| --- | --- | --- | --- |
| 1 | Intake | Safe extraction in an isolated, network-restricted container; size, file-count and path checks | Read-only repo snapshot |
| 2 | Filter and index | Skip binaries, vendored and build output; Tree-sitter chunks; symbols, imports, call graph; lexical and vector indexes | Index tables |
| 3 | Scanners (parallel) | Gitleaks + Semgrep; OSV-Scanner + ScanCode; architecture extraction | Raw evidence rows |
| 4 | Evidence store | Normalize every scanner result to the finding schema, status `scanner_confirmed` | `findings` + `evidence` rows |
| 5 | Agents | Security, Architecture and Compliance agents read evidence and retrieve cross-file context; emit new `ai_suggested` findings and notes on scanner findings | Candidate findings |
| 6 | Validation | Check each finding's cited lines really support the claim; mark `verified`, `rejected_false_positive` or `unresolved` | Validated findings |
| 7 | Risk aggregation | Deterministic scoring with floors and escalation rules | Risk assessment + rationale |
| 8 | Route | Critical goes to human review; others finalize |  |
| 9 | Report | Reporter agent writes executive summary from stored findings only; append audit trail | Report + audit log |

**Retrieval for agents.** For a finding in a function, retrieve its implementation, callers and routes, authorization middleware, DB queries, related tests and config. Combine: syntax-aware chunks, symbol lookup, file/module metadata, lexical search, semantic search, call-graph neighbours. Naive top-k semantic search alone is not enough.

**CrewAI vs LangGraph boundary.** LangGraph owns the run: stage order, state, retries, scoring, routing, pause for human review, resume. CrewAI is used inside stages 5 and 9 to define agent roles. Agents get a fixed, minimal set of read-only tools (retrieve chunk, get symbol, get call graph neighbours, read finding). If CrewAI adds no measurable benefit in the experiment, replace it with plain LangGraph nodes.

**Retry and failure paths.** A failed scanner marks that source `failed`, the run continues, and the report states the gap. An LLM call retries with backoff, then falls back to another model through the gateway, then marks affected findings `unresolved`.

## Risk scoring and security design

**Finding risk** is computed in code, not by an LLM. Starting hypothesis, to be calibrated on the benchmark and not an established standard:

```latex
risk = severity_weight \times evidence_confidence \times exposure_multiplier
```

| Factor | Source |
| --- | --- |
| Severity weight | Mapped from scanner severity or agent-assigned level (info, low, medium, high, critical) |
| Evidence confidence | Verification status and evidence quality (scanner-confirmed and verified score higher than AI-suggested) |
| Exposure multiplier | Reachability hints: public route, auth bypass, secrets in committed code, test-only code |
| Business impact | Agent-written text only; displayed, not used in the numeric score |

**Aggregation rules**

- Never average. A verified critical finding cannot be diluted by many low findings.
- Severity floor: any verified critical finding forces the repository's overall level to at least critical.
- Escalation rules for specific verified issues, such as a live-looking credential or a copyleft license in a distributed product.
- Insufficient evidence is a first-class outcome. Incomplete license data yields "insufficient evidence", never "compliant".
- Technical severity and acquisition business risk are reported separately; business risk is flagged as needing information a repository cannot provide.

**Security controls**

| Threat | Control |
| --- | --- |
| Prompt injection in repo content | Repo text enters prompts only as quoted data inside delimited blocks; system instructions never mixed with it; agents cannot change their own instructions; adversarial benchmark repos |
| Malicious archive | Extraction in a sandbox with path-traversal, symlink, size and file-count checks |
| Code execution | Audited code is never run; agents have no shell or network tools |
| Secret leakage | Detected secrets are masked before storage in prompts, logs, reports and UI; only a fingerprint and location are kept |
| Tool abuse | Explicit per-agent tool allow-list; read-only repo mount |
| Output tampering | Structured output validated against the finding schema; findings without valid file and line evidence are rejected |
| Network | Scanners and agents run with network disabled; only the LLM gateway is reachable from the agent service |
| Access | JWT auth, role checks on every endpoint, reviewer-only approval endpoints |

## API, repository layout, services and testing

**API (FastAPI, JSON, prefix `/api/v1`)**

| Method and path | Purpose | Role |
| --- | --- | --- |
| POST `/auth/login` | Get JWT | any |
| POST `/repositories` | Upload zip or give Git URL | analyst |
| GET `/repositories` | List repositories | analyst |
| POST `/repositories/{id}/audits` | Start an audit run | analyst |
| GET `/audits/{id}` | Run status, stage, cost so far | analyst |
| GET `/audits/{id}/events` | SSE stream of stage progress | analyst |
| GET `/audits/{id}/findings` | Filter by category, severity, status, file | analyst |
| GET `/findings/{id}` | Finding with evidence and code snippet | analyst |
| GET `/audits/{id}/risk` | Per-finding scores and aggregation rationale | analyst |
| GET `/reviews` | Pending critical-risk reviews | reviewer |
| POST `/reviews/{id}/decision` | Approve, override with reason, or request more evidence | reviewer |
| GET `/audits/{id}/report` | Executive report (HTML) | analyst |
| GET `/audits/{id}/report.pdf` | PDF export | analyst |
| GET `/audits/{id}/audit-log` | Append-only audit trail | reviewer, admin |
| POST `/evals/runs` | Run benchmark | admin |
| GET `/evals/runs/{id}` | Benchmark metrics | admin |

**Repository layout**

```text
/backend
  /app/api          FastAPI routers
  /app/core         config, auth, security
  /app/db           SQLAlchemy models, Alembic migrations
  /app/intake       safe extraction, filtering
  /app/indexing     tree-sitter chunking, symbols, call graph, embeddings
  /app/scanners     gitleaks, semgrep, osv, scancode adapters
  /app/retrieval    hybrid search
  /app/agents       crew definitions, tools, prompts
  /app/workflow     langgraph graph, state, routing
  /app/risk         scoring and aggregation
  /app/reports      report builder
  /app/jobs         celery tasks
/frontend           React + TypeScript
/benchmark          labeled repos, expected findings, harness
/tests              unit, integration, adversarial
/docker             compose files, scanner images
```

**Docker services:** `api`, `worker` (Celery), `scanner-sandbox` (network disabled), `postgres` (with pgvector), `redis`, `litellm`, `langfuse`, `frontend`.

**Testing:** unit tests for scoring and schema validation; scanner-adapter tests on fixture outputs; integration test per pipeline stage; benchmark runs for precision, recall and the other metrics; adversarial prompt-injection repos in CI; LangGraph pause and resume test for the review gate.

## Build plan

**Stage 1: reliable auditor.** Repo layout, Docker Compose, Postgres and migrations, safe intake, file filtering, Gitleaks/Semgrep/OSV/ScanCode adapters, normalized findings, basic HTML report, minimal upload and findings UI. Exit: scanner findings on the benchmark match the baseline.

**Stage 2: AI investigation and RAG.** Tree-sitter indexing, symbols and call graph, hybrid retrieval, Security and Architecture agents, finding validation, labeled benchmark and harness, comparison with Stage 1. Exit: documented gains or losses against the scanner baseline.

**Stage 3: orchestration and controls.** Compliance agent, LangGraph workflow with persistence, CrewAI only if justified, risk aggregation, human review gate with audit trail, authentication, SSE progress, Langfuse, cost budgets, PDF report, full UI, four-way experiment. Exit: published benchmark results.

Keep every stage runnable end to end before starting the next.
