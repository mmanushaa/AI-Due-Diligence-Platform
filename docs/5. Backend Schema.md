# 5. Backend Schema

## Entities and relationships

PostgreSQL 16 with the `pgvector` and `pg_trgm` extensions. All ids are UUIDs; all timestamps are `timestamptz` in UTC. SQLAlchemy 2 models with Alembic migrations.

| Entity | Belongs to | Purpose |
| --- | --- | --- |
| `users` | none | Accounts and roles |
| `repositories` | user (uploader) | An uploaded or linked codebase |
| `audits` | repository | One audit run and its overall state |
| `files` | audit | Indexed source files |
| `chunks` | file | Syntax-aware code chunks with embeddings |
| `symbols` | file | Functions, classes, routes, imports |
| `call_edges` | audit | Caller to callee relationships |
| `module_edges` | audit | Module import graph for cycle detection |
| `scanner_runs` | audit | One row per tool run and its status |
| `findings` | audit | Normalized findings from scanners and agents |
| `evidence` | finding | Code locations and snippets supporting a finding |
| `finding_events` | finding | Status change history |
| `risk_assessments` | audit | Aggregated result and rationale |
| `risk_factors` | risk assessment, finding | Per-finding scoring factors |
| `reviews` | audit, risk assessment | Human review request |
| `review_decisions` | review | Reviewer decision, reason, resulting level |
| `reports` | audit | Generated executive report |
| `audit_log` | none | Append-only record of actions |
| `agent_runs` | audit | Agent invocations with tokens, cost, latency |
| `eval_runs`, `eval_results` | none | Benchmark runs and per-case results |

Relationships: a repository has many audits; an audit has many files, findings, scanner runs and one current risk assessment; a finding has many evidence rows and events; an assessment has at most one review; a review has many decisions.

**files**: `audit_id`, `path`, `language`, `size_bytes`, `sha256`, `is_excluded bool`, `exclude_reason text`.

**chunks**: `file_id`, `audit_id`, `symbol_id` (nullable), `line_start int`, `line_end int`, `content text`, `content_tsv tsvector`, `embedding vector(N)` (N set by the embedding model), `token_count int`.

**symbols**: `file_id`, `audit_id`, `name`, `kind` (function, class, method, route, import, config), `line_start`, `line_end`, `signature text`, `metadata jsonb` (decorators, route path, auth markers).

**finding\_events**: `finding_id`, `from_status`, `to_status`, `actor` (system, agent name, or user id), `note`.

**risk\_assessments**: `audit_id`, `overall_level enum severity`, `overall_score numeric`, `rule_applied text` (for example, severity\_floor), `rationale text`, `technical_summary jsonb`, `business_risk_note text`, `status` (draft, pending\_review, final), `supersedes_id uuid` (nullable).

**risk\_factors**: `assessment_id`, `finding_id`, `severity_weight`, `evidence_confidence`, `exposure_multiplier`, `finding_score`, `notes text`.

**reviews**: `audit_id`, `assessment_id`, `status` (pending, approved, overridden, needs\_evidence), `requested_at`.

## Finding schema and enums

The API and agents exchange findings in this shape. Agent output that fails validation is rejected, and a finding with no valid file and line range is never stored as `verified`.

```json
{
  "category": "security",
  "title": "Potential SQL injection",
  "severity": "high",
  "confidence": 0.91,
  "origin": "agent",
  "source_tool": "security_agent",
  "verification_status": "ai_suggested",
  "verdict": "issue",
  "evidence": [
    {
      "file": "app/database.py",
      "line_start": 42,
      "line_end": 47,
      "kind": "primary",
      "snippet": "<code excerpt, secrets masked>"
    }
  ],
  "reasoning": "The query appears to be built without parameter binding.",
  "business_impact": "Potential unauthorized data access.",
  "recommendation": "Use parameterized queries."
}
```

The values above are illustrative; `confidence` is not a calibrated probability.

| Enum | Values |
| --- | --- |
| severity | info, low, medium, high, critical |
| category | security, architecture, license, dependency, secret |
| verification\_status | scanner\_confirmed, ai\_suggested, verified, rejected\_false\_positive, unresolved |
| verdict | issue, no\_issue, insufficient\_evidence |
| audit\_status | queued, running, awaiting\_review, needs\_evidence, completed, failed, cancelled |
| stage | intake, index, scanners, agents, validation, risk, review, report |
| user\_role | analyst, reviewer, admin |
| review\_decision | approve, override, request\_evidence |

## Indexes, constraints and audit-log rules

| Area | Rule |
| --- | --- |
| Dedupe | Unique `(audit_id, fingerprint)` on `findings`; fingerprint = hash of category, rule or title, file, line range |
| Lookup | Indexes on `findings(audit_id, severity)`, `findings(audit_id, verification_status)`, `evidence(finding_id)`, `files(audit_id, path)` |
| Lexical search | GIN index on `chunks.content_tsv`; `pg_trgm` GIN on `symbols.name` |
| Vector search | HNSW (or IVFFlat) index on `chunks.embedding` with cosine distance |
| Graph traversal | Indexes on `call_edges(caller_symbol_id)`, `call_edges(callee_symbol_id)`, `module_edges(from_file_id)` |
| Integrity | Foreign keys with `ON DELETE CASCADE` from audit-owned tables; `severity` and status columns use enums or check constraints |
| Evidence rule | A finding with `verification_status = verified` must have at least one `primary` evidence row (enforced in the service layer and a check query in tests) |
| Review rule | `review_decisions.reason` required when `decision` is override or request\_evidence |
| Append-only | `audit_log` and `review_decisions` have no UPDATE or DELETE grants for the app role; enforce with triggers that raise on update or delete |
| Secrets | `snippet`, prompts and logs store masked values only; keep a secret fingerprint and location, never the plaintext |
| Versioning | Risk assessments are never edited; an override creates a new row that sets `supersedes_id` |
| Retention | A scheduled job deletes repository snapshots and chunk content after `repositories.expires_at`; findings and the audit trail are kept |
| Workflow state | LangGraph checkpoints live in the same Postgres instance under a separate schema |
